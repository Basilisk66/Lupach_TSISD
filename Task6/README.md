## Проект

Реализован in-memory rate limiter на Python (только стандартная библиотека, внешних зависимостей нет).

- Алгоритм: **скользящее окно с журналом** — для каждого ключа хранятся временные метки запросов за последние `window` секунд. Запрос разрешается, если их меньше `limit`.
- Ответ `allow(key)` содержит: разрешён ли запрос, сколько запросов осталось и через сколько секунд можно повторить (`retry_after`).
- Ключи (например, API-ключи клиентов) считаются независимо.
- Потокобезопасность обеспечена `threading.Lock`.
- Часы можно подменить (параметр `clock`), поэтому тесты не используют `sleep` и работают быстро и детерминированно.
- `handle_request` имитирует API-обработчик: `200` + заголовки `X-RateLimit-*`, `429` + `Retry-After` при превышении, `401` без ключа.

### Пример использования

```python
from ratelimiter import RateLimiter

rl = RateLimiter(limit=5, window=60)
res = rl.allow("client-42")
print(res.allowed, res.remaining, res.retry_after)
```

## Как запустить тесты локально


```bash
python -m unittest discover -s tests -v
```

Всего тестов 14 штук и они проверяют следующее:

- запросы пропускаются до лимита, остаток уменьшается
- сверх лимита запрос блокируется, `retry_after` считается верно
- окно истекает, и запросы снова разрешаются
- скользящее окно освобождается постепенно, а не целиком
- ключи независимы, работает `reset`
- некорректные параметры вызывают `ValueError`
- потокобезопасность: из 200 параллельных попыток проходит ровно `limit`
- API: коды 200/429/401, заголовки, валидность `config/limits.json`

## Как устроен CI/CD

Конфигурация: `.github/workflows/ci.yml`. Состоит из двух задач

### 1. `test` (CI)

- Запускается при **каждом `push` и `pull_request`**
- Выполняет `python -m unittest discover -s tests -v`
- Если хотя бы один тест падает, команда завершается с ненулевым кодом, пайплайн становится **красным**, а деплой не запускается

### 2. `deploy` (CD, упрощённо)

- Зависит от `test` (`needs: test`) и выполняется только при `push` в ветку `main`. Pull request и другие ветки не деплоятся.
- Запускает mock-скрипт `scripts/deploy.py`, который:
  1. читает и валидирует `config/limits.json` (при ошибке деплой падает)
  2. копирует конфиг в каталог `public/`
- Каталог `public/` публикуется как **артефакт сборки** `limits-config` (`actions/upload-artifact`).

Секреты и внешние серверы не используются.

### Что считается успешным деплоем

Задача `deploy` зелёная, а в артефакте `limits-config` есть `limits.json` и `deploy.log` со строкой `deploy finished successfully`.

## Как проверить статус CI

1. Открыть вкладку **Actions** репозитория (или нажать на badge в начале README).
2. Выбрать последний запуск workflow «CI/CD»: задача `test` показывает результаты тестов по версиям Python.
3. Для запуска на `main` внизу страницы запуска в разделе **Artifacts** лежит `limits-config`, который можно скачать и посмотреть.

Ссылка на Actions: `https://github.com/<ваш-логин>/<имя-репозитория>/actions`

## Как проверить, что пайплайн действительно «краснеет»

Временно изменить ожидаемое значение в любом тесте (например, `[2, 1, 0]` на `[2, 1, 1]`) и сделать push. Задача `test` упадёт, а `deploy` будет пропущена.
