## Постановка задачи

Сортировка по времени отправления от «сейчас». Тесты: рейс в прошлом не попадает. AI-review: таймзоны (хотя бы явно зафиксировать допущение).

## Что реализовано

Было реализовано консольное приложение на Python. Расписание рейсов лежит в `data/schedule.json`
(ежедневные времена отправления по маршрутам). Приложение разворачивает его в
конкретные рейсы на сегодня и завтра, отбрасывает ушедшие и выводит ближайшие,
отсортированные по времени отправления.

Структура проекта:

```
transport/
  models.py      # Trip — один рейс (departs_at обязательно с часовым поясом)
  timetable.py   # загрузка JSON, валидация, разворачивание расписания по датам
  service.py     # nearest_departures() — основная логика включающая фильтр и сортировку
  cli.py         # консольное демо
data/schedule.json
tests/           # unittest-тесты
docs/ai-review.md
docs/prompts.md
```

### Принятые допущения

1. Всё расписание хранится в одном часовом поясе — он указан в `schedule.json` (`"timezone"`).
2. Расписание действует каждый день (нет выходных, праздников, сезонности).
3. «Сейчас» и время рейсов — всегда aware-datetime. Наивное время отклоняется с `ValueError`,
4. Рейс, отправляющийся ровно в момент «сейчас», считается доступным.
5. Переход на летнее/зимнее время не обрабатывается специально.

## Работа с ИИ

### Использованные инструменты
- В качестве ИИ-ассистента использовал Claude: генерация черновика кода, тестов и ревью.
- Запуск и проверка кода — локально, вручную.

### Ключевые промпты
1. Спроектировать структуру и зафиксировать допущения (часовые пояса, граница «ровно сейчас»).
2. Сгенерировать модели и функцию `nearest_departures` с явными правилами.
3. Сгенерировать unit-тесты, включая «рейс в прошлом не попадает» и пограничные случаи.
4. Попросить ИИ найти краевые случаи, которые тесты не покрывают.
5. Провести AI-ревью кода (безопасность, читаемость, таймзоны, упрощение).

### Что ИИ сделал хорошо
- Сразу же предложил разделение на модели, расписание, сервис и CLI.
- Предложил использовать `zoneinfo` и aware-datetime вместо наивного `datetime.now()`.
- Сгенерировал широкий набор тестов, включая сравнение времени в разных поясах.
- Заметил переход через полночь (рейс завтра в 00:10, когда сегодня рейсов уже нет).

### Что ИИ сделал плохо / что исправлено вручную
- В тесте CLI неверно задан ожидаемый результат (`08:05` ожидался в выводе при «сейчас» 08:10 —
  то есть рейс в прошлом). Тест был исправлен.
- Без явного указания использует наивный `datetime.now()` — переписано на aware-время.
- Срез `upcoming[:limit]` при `limit <= 0` даёт результат (`[:-1]` вернёт почти всё) —
  решил добавить валидацию `limit >= 1` и тест к нему.
- Первоначально расписание разворачивалось только на «сегодня» — добавил `days=2`.
- Предлагалось «оптимизировать» через `heapq.nsmallest`, решил не внедрять так как посчитал слишком "запарным" для учебного объёма данных.

### Риски и ограничения
- **Галлюцинации API:** ИИ может «придумать» несуществующий параметр (например, `ZoneInfo(...).localize()` — это метод `pytz`, а не `zoneinfo`).
  Всё проверено запуском кода и тестов.
- **«Уверенный» неверный код:** модель выдаёт неправильный тест с тем же тоном, что и правильный. Доверять можно только прогону тестов и собственному чтению.
- **Утечка данных:** в промпты не передавались персональные данные и секреты; расписание — вымышленное.
- **Лицензии:** сгенерированный код — типовой, но возможное сходство с публичными фрагментами не исключено; код прочитан и переработан вручную.
- **Ограничения решения:** одно расписание на все дни, один часовой пояс, нет обработки DST (см. `docs/ai-review.md`).
